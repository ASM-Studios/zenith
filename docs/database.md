# Database

Postgres 17, accessed from `apps/api` through Drizzle ORM (`drizzle-orm` + `postgres` driver). Schema changes go through SQL migrations generated by `drizzle-kit` and committed to git.

## Layout

| Path | Content |
| --- | --- |
| `apps/api/src/db/index.ts` | Drizzle client, reads `DATABASE_URL` |
| `apps/api/src/db/schema/` | Tables, one file per domain, all re-exported from `index.ts` |
| `apps/api/src/db/schema/auth.ts` | Better Auth tables, **generated** — never edit by hand |
| `apps/api/src/db/migrate.ts` | Applies pending migrations |
| `apps/api/drizzle/` | Generated SQL migrations + `meta/` snapshots — committed |
| `apps/api/drizzle.config.ts` | drizzle-kit config |

## Network

Postgres has no published port: it is only reachable from containers on the compose `backend` network. Nothing in the workflow below needs it from the host except applying migrations, which runs in a container.

| Step | Command | Runs on | Needs the database |
| --- | --- | --- | --- |
| Change the schema | edit `src/db/schema/` | host | no |
| Generate the migration | `npm run db:generate -w @zenith/api` | host | no |
| Review and commit | `git add apps/api/drizzle` | host | no |
| Apply | `migrate` service | container, `backend` network | yes |

`db:generate` diffs the TypeScript schema against the last snapshot in `drizzle/meta/`; it never connects to Postgres. `drizzle-kit push`, `studio` and `introspect` do need a connection and are not used. If Studio is ever needed, publish the port on `127.0.0.1` only, in a local `compose.override.yml`.

## Changing the schema

1. Describe the table in TypeScript:
   - To change an existing table, edit its file in `apps/api/src/db/schema/`.
   - To add a table, create a new file there, for example `favorites.ts`, then add one line to `apps/api/src/db/schema/index.ts` so drizzle-kit and the client see it:

     ```ts
     export * from './favorites.ts';
     ```

2. `npm run db:generate -w @zenith/api -- --name <changes>` writes `drizzle/NNNN_<changes>.sql`.
3. Read the SQL, then commit it together with the schema change.
4. `podman compose up -d --build`. The `migrate` service applies pending migrations before `api` starts; `api` does not start if it fails.

To apply without restarting everything: `podman compose run --rm --build migrate`.

Rules:

- Never edit a migration that is committed or applied anywhere. Fix forward with a new one.
- Never generate migrations in the Dockerfile or at startup. They would be unreviewed, unversioned, and could diverge from what a database already applied.
- A new `NOT NULL` column without a default fails on a table that has rows. Add a default, or reset the dev database.

## Auth tables (Better Auth)

The tables `user`, `session`, `account` and `verification` (plus the `username` plugin columns) are defined by Better Auth, not by hand. After changing `apps/api/src/lib/auth.ts` in a way that affects storage, for example adding a plugin:

```sh
npm run auth:generate -w @zenith/api   # rewrites src/db/schema/auth.ts
npm run db:generate -w @zenith/api     # migration for the difference
```

`auth:generate` only loads the config; the placeholder `DATABASE_URL` and `PASSWORD_PEPPER` in the script exist so the config can be imported, and nothing connects. Customise names or fields through Better Auth options, then regenerate.

## Resetting the dev database

Migrations on an empty database create everything, so "creating the database" and "migrating" are the same operation. Postgres itself creates the database and role from `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` the first time the `pgdata` volume is empty.

Start from an empty database (deletes all data):

```sh
podman compose down -v
podman compose up -d --build
```

Squash the migration history into a single `0000`, only while no other database has applied the current migrations:

```sh
rm -rf apps/api/drizzle                 # whole folder, meta/ included
npm run db:generate -w @zenith/api
podman compose down -v                  # required, the database must be empty
podman compose up -d --build            # rebuild, the image embeds drizzle/
```

Deleting `drizzle/` without `down -v` breaks startup: the new `0000` tries to create tables that already exist. Keeping `meta/` makes `db:generate` see no change. Once a teammate's or a deployed database has applied migrations, the history is never rewritten again; only new migrations are added.
